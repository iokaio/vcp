# Sustained execution qualification workloads

Work item: EE-07. These workloads are defined before execution and remain **unrun**. They extend independently passing, freshly scaffolded A and B applications through the same locally compiled execution engine. A retained repair checkpoint is useful diagnostic evidence but cannot supply the fresh-scaffold prerequisite. [Experiment guidance](execution-engine-experiments.md) governs evidence and interpretation; the [work ledger](../plan/25-execution-engine-refinements.md) records actual results.

Before either workload begins, preserve the starting workspace manifest, passing original scorecard, protected test hashes, candidate version/hash and source revision, exact provider/model/endpoint, process/check profiles and database identity where applicable. Retain each stage's authored diff, independent checks, authorized inspection bundle, analysis index and review. No result is qualified solely by model prose or native completion. No live execution is authorized by this document while the outstanding spend confirmation remains unresolved.

## E-A: TaskBoard portable data and recovery

Start from the fully passing Scenario A application. Extend its existing API, persistence and Vue interface with a versioned JSON export/import workflow. Keep existing task fields, validation, filtering and API behavior. Use the installed toolchain and dependencies unless the implementation demonstrates a concrete need for another dependency.

| Stage | Requested work | Independent acceptance |
|---|---|---|
| A1 | Add `GET /api/tasks/export` returning `{schemaVersion:1,tasks:[...]}` with every task and its stable ID. Export persisted data in a deterministic ID order. | Create representative tasks, restart the server, export, and compare every documented task field with the original API. Empty export is valid. Existing routes and protected tests pass. |
| A2 | Add `POST /api/tasks/import` accepting that format with atomic merge by ID. New IDs create tasks; an existing ID with identical fields is a no-op; an existing ID with different fields causes the whole import to fail with 409 `IMPORT_CONFLICT`. Invalid version, duplicate IDs within the document or any invalid task produces 400 `VALIDATION_ERROR` and no write. | Independently snapshot data before valid, repeated, mixed-valid/invalid and conflicting imports. Verify exact after-state, no partial writes, stable IDs and unchanged data after restart. Test Unicode, empty input list and multiple records. Repeating an identical import changes nothing. |
| A3 | Add accessible export/download and import/file-selection controls, progress/error feedback and an import summary to the existing Vue UI. | Build and component tests; browser review verifies keyboard use, visible errors, retained task state on rejection and a successful export/import round trip. Record screenshots only when the browser was actually inspected. |
| A4 | Explicitly pause at a recorded task checkpoint after an API/UI edit and verification. Close the owner, reopen for read-only inspection, then deliberately resume the same task with a requirement to document the data format and recovery behavior. | Reopen produces no new provider send or application effect. Resume retains the task ID and existing files, refreshes current instructions and preserves protected test hashes. No operation repeats merely because its outcome was previously uncertain. |
| A5 | Exercise one declared external-change fault: alter one import validation branch in the isolated workload after capturing a passing checkpoint, then request repair against the unchanged acceptance contract. | The independent invalid-import check fails before repair and passes after repair. Retained evidence explains the source revision change, failed check, corrective edit and fresh full verification. Do not manufacture a passing result by changing the protected acceptance test. |
| A6 | Produce the final local build, format documentation and regression report. | All original A gates plus A1–A5 checks pass from a restarted application. Review the API/UI behavior and exported data for completeness. List any untested browser behavior separately. |

This workload exercises repeated server/client/schema/test/documentation reads, more than one repair context, cross-session instruction refresh and preservation of application data. Its quality evidence is independent of token count and elapsed time. If the check runner cannot exercise browser behavior, that criterion stays untested.

## E-B: Inventory stock adjustments and durable audit

Start from the fully passing Scenario B application with its isolated SQL Server database. Add an explicit stock-adjustment workflow and append-only business audit records. Preserve existing product CRUD, validation and optimistic-concurrency behavior. Use integer quantities; do not introduce external services or use an unrelated database.

| Stage | Requested work | Independent acceptance |
|---|---|---|
| B1 | Add a migration and audit entity with adjustment ID, product ID, signed delta, before/after quantity, reason, timestamp and caller-supplied operation ID. | Apply migrations to a fresh isolated database and to a copy of the passing B database. Existing product data remains intact. Audit records have the required fields and a unique operation ID enforced by the database. |
| B2 | Add `POST /api/products/{id}/adjustments` accepting `{operationId,delta,reason,rowVersion}`. Atomically change quantity and add exactly one audit record. Reject zero delta, blank reason or negative resulting stock with 400; preserve the application's established missing-product and stale-version behavior. | Verify positive/negative adjustments, missing product, stale version, invalid inputs and concurrent requests. Rejected requests leave both stock and audit unchanged. Successful response includes the current product version and adjustment ID. |
| B3 | Define idempotent retry: the same operation ID with identical product, delta and reason returns its original adjustment without another stock change; a different payload for that ID returns 409 `OPERATION_CONFLICT`. Add read-only audit history ordered by adjustment time and ID. | Repeat a successful operation before and after server restart, including its original row version; stock changes once and only one audit row exists. A conflicting retry changes nothing. Independent SQL and API observations agree. |
| B4 | Add a Razor Pages adjustment form and audit view with clear validation/concurrency messages. Pause after a recorded edit/check checkpoint, close and reopen the VCP owner, then deliberately resume. | Browser review and UI tests; read-only reopen causes no provider send, migration, adjustment or duplicate tool effect. Resume uses current source/instructions and the same task. Original protected test hashes remain intact. |
| B5 | Inject one documented stale-source change in the isolated workload and request a repair of an independently failing adjustment/concurrency check. | Evidence identifies the changed source, actual failed check, repair edit, full fresh check set and final result. Existing optimistic-concurrency behavior remains correct; no relaxation of the protected assertions is permitted. |
| B6 | Produce a local publish directory and regression report; start that local artifact for smoke checks. | Original B gates and B1–B5 pass, including migrated database persistence across restart and independent SQL counts. Review form usability and the audit record semantics. No external deployment or VCP release occurs. |

Record the operation IDs used by independent checks and separate application idempotency from VCP's own provider/tool attempt identities. A paid inference retry must never be justified merely because the application endpoint happens to support idempotency.

## Evidence review and acceptance

Each workload needs a stage-by-stage matrix of passed, failed, blocked and untested criteria with concrete artifact references. Analyze observed quality, diagnostic completeness and fast-state/context behavior separately. Report actual phase sample counts, known and unknown usage, allocation changes, source-range reuse, repairs, explicit stop/reopen behavior and evidence omissions. Do not sum overlapping timings or claim a stable percentile from one observation.

An unchanged repeated failure is investigated before another paid attempt. A no-progress pause retains its evidence and requires deliberate resume. Any unavailable credential, provider authorization, database prerequisite or independent gate is an explicit missing criterion. These workload definitions do not waive the pending constraint work, authorize removal of a spending cap or count as execution evidence.
