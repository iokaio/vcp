### Provider stop shared by both runs

A recorded 18 model attempts (15 settled, three retained liabilities); B recorded
21 (18 settled, three retained liabilities). All six failing responses were
HTTP 429 with `limit_source: upstream_provider_shared_pool`, reporting temporary
upstream throttling. They had no qualified usage or generation identifier that
could settle their charge. The previous 100/200 ms retry delays rapidly retried
the same throttled route, and the final task reason only reported accounting
reconciliation.

The harness's `3.00 USD (incomplete cost evidence)` reserves the full task cap;
it is not evidence that either run actually incurred a $3 charge. Submitted
liabilities remain unresolved. This fix does not erase them, invent zero usage,
silently change endpoints, or automatically resume the old tasks.

Separate local projects do not provide separate upstream capacity. The evidence
establishes shared-pool throttling; it does not establish that running A and B
together caused it.

### B: file creation could not create parent directories

After an initial malformed patch, valid Add File requests targeting
`src/Inventory.Web/Data/InventoryDbContext.cs` repeatedly failed with Windows
error 2 because `Data` did not exist. Patch preparation required a parent handle
before an authorized creation could occur. The ten successful tool effects were
reads/lists; no application changes were written. The missing DbContext,
migration and seed-data failures were downstream consequences.

The correction prepares an immutable parent-directory plan without writing.
Missing parents are explicit write resources; existing ancestors are bound by
native identity. Dispatch creates one authorized component at a time using an
atomic parent-relative native create that returns a pinned handle. It rejects
intervening entries and junctions, handles shared case aliases, and retains
partial-effect evidence. Recovery observes directories without assuming who
created them, deleting them, or replaying an uncertain edit. Rename destinations
still require existing parents.

### B: ambient baseline hid a real process bootstrap defect

The harness's ambient `dotnet build` passed. The actual `vcp_exec` build failed
inside `NuGet.targets(780,5)` with `Value cannot be null (Parameter 'path1')`.
A minimal .NET 10 reproduction traced this to the scrubbed environment lacking
`PROGRAMFILES`, followed by `APPDATA`.

The process profile now permits five explicit public bootstrap keys:
`PROGRAMFILES`, `PROGRAMFILES(X86)`, `APPDATA`, `LOCALAPPDATA`, and
`DOTNET_CLI_HOME`. B supplies Windows installation paths and fresh run-owned
directories for the latter three. It does not inherit account credentials,
NuGet user configuration, arbitrary environment variables, or startup hooks.
Values remain part of the profile's authority digest.

### A: unfinished generated code

A's retained patch and on-disk file both contain `await loadTasks()` inside a
non-async function. The generated tests also have TypeScript `unknown` errors.
No process verification ran before the provider pause. This is unfinished model
output, not evidence that VCP corrupted a successful patch. The typecheck,
test and HTTP failures are valid; their assertions remain intact. The existing
project and failed run were preserved for investigation.

## Harness and runtime corrections

- Each launcher child starts in its selected standalone project. A-D have
  separate project, data and profile paths; VCP checkout paths, nested Git
  projects and link/junction aliases are rejected. No shared VCP source project
  is used as a scenario workspace.
- Inventory reuse accepts either supported local tool-manifest location without
  rewriting the project.
- All scenarios probe the real toolchain with the exact cleared profile
  environment before inference: A typecheck, B local-tool restore/build,
  C Maven tests, D pytest. Required failures prevent paid admission.
- Rate limits use 5/10-second backoff, respecting qualified Retry-After up to
  60 seconds, retry ceilings and the original deadline. This cannot guarantee
  that an external shared pool becomes available.
- A bounded, allowlisted provider diagnostic links the failed attempt to raw
  evidence and explains the HTTP status and limit source. Task status and the
  harness retain that explanation alongside unresolved accounting.
