## Findings

1. **Setup succeeded.** The provider was reused, dependencies and baseline passed,
   and the previously corrected short-deadline profile passed `setup check`.
2. **T1 stopped for process approval.** The pending operation was `vcp_exec`,
   profile `node`, arguments `--test tests/tasks.api.test.ts`. VCP's process
   preparation assigns read, write, execute, network, install, publish and opaque
   effects to every process. The scenario profile intentionally excludes publish.
   Autonomous mode does not override this policy. The non-interactive owner closed
   with exit 4 and a pending approval. `vcp_verify` uses the same process preparation,
   so changing the tool name would not remove this requirement. No publishing
   permission was added and no approval was granted by this review.
3. **Generated application failures were real.** The model's API tests omitted imports
   for `beforeEach` and `afterEach` and accessed JSON responses typed as `unknown`.
   The application accepted impossible date `2026-02-30`, and malformed JSON returned
   Express HTML instead of the required JSON error. These acceptance checks remain.
4. **The harness also produced a false failure.** `api.create` passed a string ID to
   a Boolean assertion parameter. PowerShell rejected the argument even though the
   API returned a valid ID. The gate then failed to save the created task, leading
   dependent PATCH, persistence and DELETE checks to request an empty ID. The invalid
   date request also inserted an extra task, explaining the list-count failure.
5. **The harness continued after a blocked task.** It started a repair and the next
   feature despite required input. These are not ordinary failed build/test outcomes;
   starting a new paid task does not resolve the original approval.
   Repair prompts also omitted the original task's environment and protected-file
   instructions. The repair proposed `node npm run typecheck`, although the original
   task specified the absolute `npm-cli.js` path. That malformed command was blocked
   before execution by the same approval boundary.
6. **Later provider accounting was incomplete.** T2 and its repair paused with
   `provider outcome requires accounting reconciliation`. Retained attempts include
   `provider failure retained before bounded retry` and `retained response did not
   complete`. The final summary's approximately USD 3.10 is conservative harness
   accounting, including a reserved task cap, not proof of that amount being charged.
   The scorecard correctly reports `spend_evidence_complete: false`. The owner's stop
   report alone does not establish the cause of each provider failure.

## Fix scope and verification

The harness corrections address the Boolean ID assertion, misleading dependent API
checks, and admission of further paid work after blocked execution. They retain
the actual application failures, approval requirements and unsettled-cost evidence.
The interrupted project is not silently repaired or reset by these changes.

Implemented corrections:

- Scenario A validates a nonblank ID with an explicit Boolean expression. If create
  fails, dependent checks remain required and are recorded as blocked skips; they
  no longer send requests with an empty ID. Independent checks still run.
- The shared harness records the first observed execution block in
  `results/paid-execution.json`, with reasons, task/session, approval IDs and links
  to command, policy and tool evidence. It collects read-only evidence, then refuses
  the next paid admission and exits through normal result finalization. It does not
  proceed to later fixture mutations or packaging after that refusal.
- A normal deadline pause permits only a continuation of the same recorded task.
  Approval, unresolved effects, internal failure, cancellation, invalid configuration,
  budget exhaustion and observed interrupted output prevent further paid work.
- Repair prompts include the original task, tool instructions and protected-file
  constraints in addition to the failed checks.

Verification on October 3, 2026: all eleven offline suites passed (`Harness`,
`Accounting`, `CommandLog`, `Launcher`, `ProfileDeadlines`, `ProjectContext`,
`ProjectReuseAB`, `ProjectReuseCD`, `ProviderReuse`, `ScenarioGates`, and
`BlockedExecution`). The new blocked-execution/repair suite passed 196 checks.
PowerShell parsing and `git diff --check` also passed.
No paid provider run or durable task recovery was performed during this review.

Remaining: the installed CLI's process-approval limitation, the generated application
defects and the interrupted run's unreconciled provider accounting are not resolved by
these harness changes. Reusing the unfinished project can correctly fail its baseline
checks. This review does not claim a successful full scenario or a reconciled bill.
